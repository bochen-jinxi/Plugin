文件：PluginDemo.csproj

【3】瑕疵 5.2 修复：泛型委托字段改为 readonly + 构造函数注入
--------------------------------------------------------------------------------

3.1 PluginBase<TContext>
    文件：Plugins\PluginBase{TContext}.cs
    变更：
        - protected Func<TContext, string> DescribeFunc;
          -> private readonly Func<TContext, string> _describeFunc;
        - 新增 protected 构造函数 PluginBase(Func<TContext, string> describeFunc)，
          对 null 抛 ArgumentNullException，否则赋值给 _describeFunc；
        - Initialize 中 DescribeFunc(context) 改为 _describeFunc(context)。
    效果：描述函数在构造时一次性注入，运行期不可变，子类无法在普通方法中
    误改它，保证策略不变性。

3.2 GenericPlugin<TContext>
    文件：Plugins\GenericPlugin.cs
    变更：
        - 删除 public GenericPlugin() { DescribeFunc = ctx => ...; }
        - 改为 public GenericPlugin() : base(ctx => $"BaseTag: {ctx.BaseTag}") { }
    效果：通过基类构造函数参数注入 lambda，语义更直接。

3.3 PluginContextStrategyBase<TPlugin>
    文件：Hosting\Strategies\PluginContextStrategyBase{TPlugin}.cs
    变更：
        - protected Func<TPlugin, IServiceProvider, IPluginConfig, IPluginContext> CreateContextCoreFunc;
          -> private readonly Func<...> _createContextCore;
        - 新增 protected 构造函数接收 createContextCore，null 校验后赋值；
        - CreateContext / CreateContext(TPlugin) 内部 CreateContextCoreFunc(...)
          改为 _createContextCore(...)。
    效果：上下文构造函数在构造时一次性注入，运行期不可变。

3.4 GenericPluginContextStrategy
    文件：Hosting\Strategies\GenericPluginContextStrategy.cs
    变更：
        - public GenericPluginContextStrategy() { CreateContextCoreFunc = ...; }
          -> public GenericPluginContextStrategy() : base((plugin, services, config) => ...) { }
        - 补充类注释说明匹配 GenericPlugin<BasePluginContext> 及其派生类。

3.5 SamplePluginContextStrategy
    文件：Hosting\Strategies\SamplePluginContextStrategy.cs
    变更：
        - 原构造函数体内赋值 CreateContextCoreFunc 并捕获 _env 字段；
        - 改为通过 base(...) 注入 lambda，在 lambda 内直接用 env.EnvironmentName
          （env 在构造函数参数作用域内可见）；
        - 保留 env 的 null 校验（在构造函数体内 _ = env ?? throw ...）；
        - 补充类注释说明匹配 GenericPlugin<SamplePluginContext> 及其派生类
          （如 SamplePlugin）。
    效果：消除 _env 字段，env 仅用于构造期读取环境名，策略对象本身更不可变。

【4】瑕疵 5.3 修复：BasePluginContext 配置降级逻辑加注释
--------------------------------------------------------------------------------

文件：Abstractions\BasePluginContext.cs
变更：在 _config = config as PluginConfig ?? new PluginConfig(...) 这一行前
    补充注释，明确说明：
    - 基类只关心基类配置 PluginConfig；
    - 当传入派生配置（如 SamplePluginConfig）时 as 会成功，派生专属字段
      （如 Environment）不会在基类层面可见，这是有意为之；
    - 当传入的不是 PluginConfig 体系时，回退到等价的 PluginConfig。
原因：原代码静默降级，缺少注释容易让人误读为 bug。
影响：无功能变化，仅增加 4 行注释。

--------------------------------------------------------------------------------
【5】瑕疵 5.4 修复：PluginHost 策略匹配语义改为"首个命中"
--------------------------------------------------------------------------------

文件：Hosting\PluginHost.cs
变更：
    - 删除 applied 计数器与 foreach 遍历所有匹配策略的循环；
    - 改为 var strategy = _strategies.FirstOrDefault(s => s.CanHandle(plugin));
    - 若 strategy is null，输出 LogWarning "Plugin {Name} has no matching
      strategy. Skipped." 并 return；
    - 否则构造 context、plugin.Initialize(context)，并输出 LogInformation
      "Plugin {Name} started with strategy {Strategy}."（含策略类型名）。
原因：原代码一个插件可能匹配多个策略，导致 Initialize 被多次调用（虽然幂等
    只第一次生效），日志说"N context(s)"与实际"只有第一个生效"语义不一致。
    改为"首个命中"后，语义清晰：一个插件对应一个策略，多匹配视为配置错误
    应在 DI 注册期避免。
影响：
    - 行为变化：原代码若多策略匹配会多次调用 Initialize（第二次被幂等跳过），
      现在只调用一次。对当前 DI 注册（每个插件只有一个匹配策略）行为完全一致；
    - 日志变化：从"started with N context(s)"变为"started with strategy
      {Strategy}"，更准确；
    - 新增"无匹配策略"的 warning，原代码会静默跳过（applied=0，日志说"0
      context(s)"），现在显式告警。

【6】瑕疵 5.1 复核：未修改
--------------------------------------------------------------------------------

原报告 5.1 指出 SamplePluginContextStrategy 的泛型参数是
GenericPlugin<SamplePluginContext>，而 SamplePlugin 继承
GenericPlugin<SamplePluginContext>，CanHandle 用 is 判定能匹配。
经复核：这是正确的设计——策略匹配的是"能处理该插件类型的策略"，依赖 is
的多态性是预期行为。原报告也承认"这一点是通的"。本次改造在两个策略类上
补充了类注释说明匹配关系，可读性问题已解决，无需结构修改。故 5.1 不单独
列为修改项。
